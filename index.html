A build system for AI-coding harnesses.

A harness (the rules, agents, commands, skills, hooks and MCP servers that shape coding agents) kept as source in one Git repository, the Forge. Craftar composes it per team, writes each tool's own files and records them in a lockfile (P1, P2).

Two problems, one root: the harness has no source and no record.

P1

One harness, T teams, K AI coders, A agents each: maintained by hand.

The same agents, rules, commands, hooks and MCP servers live as T copies in K formats (.claude/, .kiro/, AGENTS.md, .cursor/). A change costs T × K manual edits, with no record of what came from what.

requiresone source; emission per target; a record per file.

P2

One developer, many workspaces, separate remotes.

One workspace per team, each on that team's Git host, its harness copied in by hand. Nothing records which version each one carries, or whether a file was edited in place.

requiresa channel that is no team repository's remote; a lock per workspace; a registry.

What breaks when the harness is duplicated: observed, not hypothetical.

Eight failures seen in two earlier generators and in hand-synced workspaces: FM-1 to FM-5 from P1, FM-6 to FM-8 from P2. Each becomes a constraint in Invariants.

Source, resolution, emission.

Ingredients are source; recipes and profiles compose them; craftar sync resolves them for one workspace, writes each target's files and records them in a lockfile. Generated files are committed, so a team that only uses Kiro never needs Craftar installed.

P1 resolved: solid edges are generated and recorded in each workspace's lockfile; status reads it to report drift per workspace.

P2 resolved: one Forge, one lock per workspace, one registry

The Forge is a fifth repository that no team repository references; each workspace's craftar.yaml points to it, and its lock records the Forge commit that produced it. craftar workspaces reports each one as up to date, outdated (forge moved when the Forge has a newer commit) or drifted.

the Forge is never a remote of a team repository; generated files are committed inside each workspace.

From layers to files: how sync works.

Layers apply weakest first and the strongest wins; stack recipes that share a slot exclude each other, and {{params}} come from the winning layer. craftar explain <file> names the layer behind each output.

Layers, weakest → strongestsource
baserecipe · every workspace
stack recipesbackend-clean-arch · frontend-angular
team profileprofiles/team-a
craftar.yamlthis workspace · committed
craftar.local.yamlone developer · git-ignored

All layers are versioned in the Forge except the last two, which live in the workspace.

resolve
Pipelinecraftar sync
$ craftar sync
  1. Read craftar.yaml; load the Forge: a path, or a git URL at a ref, cached per machine.
  2. Resolve layers, exclusive slots and params into the final ingredient set.
  3. Emit the open standards (AGENTS.md, Agent Skills, mcp.json) through the target emitters.
  4. Emit each tool's own format through one Craftar emitter per target.
  5. Diff against craftar.lock; classify each file (new · update · unchanged · adopt · drift · collision · orphan); write, remove orphans, refresh the lock.

What syncs where

Craftar writes only each AI coder's own files: every path is in the capability matrix: and a root AGENTS.md, read by Codex, Cursor, Copilot, Antigravity, OpenCode, Warp and Kimi; plus .craftar/ when the recipes bring a local service. Folders like src/ or infra/ are never touched: only paths recorded in craftar.lock are written or removed. Outside the workspace and the Forge it writes only under ~/.craftar: the Forge cache and the registry.

Growing the Forge: a second client, one base

A second client imported into the Forge reuses every ingredient that matches; the ones that differ become variants named after the profile, so both workspaces still reproduce byte for byte. forge variants lists them, forge diff classifies each hunk, and forge unify resolves one, keep a side, move a differing value into the profile as a parameter, or a block as a section, after planning every registered workspace that reads the Forge.

one rule, two clients. forge unify refuses when another layer, profile or ingredient already uses the key; forge promote makes a profile's variant the base.
